# Backup & Disaster Recovery

Production entry point: [`deploy/backup.sh`](deploy/backup.sh), installed by [`deploy/setup-backups.sh`](deploy/setup-backups.sh). The work is done by `scripts/backup-db.sh`, `scripts/backup-files.sh`, `scripts/restore-db.sh`, `scripts/restore-drill.sh` (shared helpers in `scripts/lib-backup.sh`).

**Verified in Phase 1** (see `PHASE1_REPORT.md` → Deployment validation): against the real compose stack (MySQL 8.4 container), a backup was taken, shipped to an rclone remote and verified there, restored into a scratch database by the drill (schema checked against `prisma/migrations` with the deployed image, row counts checked), and the files archive restored byte-identical. A failed backup (database down) and a failed drill (corrupted file) both delivered an alert to the webhook. A half-applied migration was rolled back exactly with `RESTORE_DB_DROP_FIRST=1`. The one thing that could not be exercised here is a real off-host provider account (B2/S3/SFTP) — the rclone path was tested against a local rclone remote.

## Turning it on (once, on the VPS)

```bash
cd /opt/dostoori
apt-get install -y rclone && rclone config        # an off-host remote you control
# .env:
#   BACKUP_ENCRYPTION_PASSPHRASE   generated by setup-vps.sh — COPY IT OFF THIS HOST
#   BACKUP_RCLONE_REMOTE="<remote>:<bucket>/dostoori"
#   BACKUP_REQUIRE_OFFHOST="1"                     # a failed upload is a failed backup
#   BACKUP_ALERT_WEBHOOK="https://..."             # Slack/Discord/ntfy/healthchecks webhook
#   BACKUP_RETENTION_DAYS="14"  BACKUP_REMOTE_RETENTION_DAYS="90"
bash deploy/setup-backups.sh
```

`setup-backups.sh` takes a real backup, runs a restore drill on it, and installs `/etc/cron.d/dostoori-backup` **only if the drill passes**:

| When (UTC) | What |
|---|---|
| daily 03:17 | `deploy/backup.sh all` — database + uploaded files |
| monthly, 1st, 04:37 | `deploy/backup.sh drill` — restore the newest DB backup into a scratch DB and verify it |
| every deploy | `deploy/deploy.sh` runs `deploy/backup.sh db` before migrating, and refuses to deploy if it fails |

Logs: `backups/backup.log`, `backups/drill.log`. The host needs Docker and rclone only — `mysqldump`/`mysql` run inside the `db` container (docker mode, `BACKUP_DB_SERVICE=db`).

## What gets backed up

| What | Script | Contains |
|---|---|---|
| MySQL database | `scripts/backup-db.sh` | offices, users (password hashes, encrypted 2FA secrets), clients, cases, invoices, audit logs, … |
| Uploaded documents | `scripts/backup-files.sh` | `storage/case-documents/` — the files the `Document` table points to |

Restore both from close points in time; a `Document` row without its file (or the reverse) is useless.

## Guarantees each run checks

- **Encrypted before it touches disk**: `openssl enc -aes-256-cbc -pbkdf2`, key `BACKUP_ENCRYPTION_PASSPHRASE` (separate from the app's secrets). Files are `chmod 600`, directories `700`.
- **Complete**: the DB dump is decrypted and must end with mysqldump's `-- Dump completed` marker; the files archive must decrypt and list cleanly. Otherwise the temp file is discarded and the run fails.
- **Off-host**: with `BACKUP_RCLONE_REMOTE` set, the copy is verified by size on the remote; with `BACKUP_REQUIRE_OFFHOST=1`, a missing/failed remote fails the run.
- **Retention**: local copies older than `BACKUP_RETENTION_DAYS` (default 14) are deleted; remote copies older than `BACKUP_REMOTE_RETENTION_DAYS`, if set.
- **Alerting**: any non-zero exit of a backup or drill POSTs `{"text": "dostoori … FAILED …"}` to `BACKUP_ALERT_WEBHOOK` (and says so in the log if none is configured).

## Keys you must keep elsewhere

- `BACKUP_ENCRYPTION_PASSPHRASE` — without it every backup is unreadable.
- `TWO_FACTOR_ENCRYPTION_KEY` — restoring into an environment with a different key makes users' 2FA secrets unusable.

Store both in a password manager / vault, not only on the VPS.

## Restoration procedure

```bash
cd /opt/dostoori
set -a; . ./.env; set +a
export BACKUP_DB_SERVICE=db

# 1. First into a scratch database, and look at the row counts it prints:
bash scripts/restore-db.sh backups/db/dostoori-db-<timestamp>.sql.gz.enc dostoori_restore_check

# 2. Then for real. RESTORE_DB_DROP_FIRST=1 makes the result EXACTLY the
#    backup (without it, tables the backup doesn't contain survive — e.g. one
#    created by a migration that failed half way). Stop the app meanwhile.
docker compose stop app
RESTORE_DB_DROP_FIRST=1 bash scripts/restore-db.sh backups/db/dostoori-db-<timestamp>.sql.gz.enc
docker compose start app

# 3. The matching files backup into storage/:
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_ENCRYPTION_PASSPHRASE \
  -in backups/files/dostoori-files-<timestamp>.tar.gz.enc | tar -xz -C /opt/dostoori
chown -R 1000:1000 storage
```

Off-host copies: `rclone copy "$BACKUP_RCLONE_REMOTE/db/<file>" backups/db/` first.

The pre-migration restore point of the last deploy is recorded in `.deploy/last_backup`.

## Verification

- `bash deploy/backup.sh drill [file]` — restores into `dostoori_drill_<timestamp>`, runs `prisma migrate status` against it from the deployed image (schema must equal `prisma/migrations`), requires non-empty `Office`/`User`, compares row counts with the last passing drill (`backups/drill-baseline.txt`), reports RTO/RPO, and always drops the scratch database. Warns when the newest backup is older than 26 h.
- The drill does not boot the app. Quarterly, also rehearse end to end: restore DB + files into a staging stack, log in, open a case document, and complete a 2FA login.

## Direct mode (no Docker)

Without `BACKUP_DB_SERVICE`, the scripts use host `mysqldump`/`mysql` and `DATABASE_URL` (parsed by `scripts/lib-db-url.mjs`, so Node is needed), e.g. for a non-Docker install or a local developer database.

## What this does not cover

- **Point-in-time recovery.** Periodic full dumps: you restore to the last backup, not to an arbitrary second. Add MySQL binlog-based PITR if that matters.
- **Provisioning the off-host account** (Backblaze B2, S3-compatible, SFTP to another host) — a one-time manual step outside this repo.
- **The dashboard's `/dashboard/backup` page** remains disabled; backups are a server-side operator job.
